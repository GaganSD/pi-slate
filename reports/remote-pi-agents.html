Research brief · remote worktrees + subagents

Where should my Pi agents run?

For an 8 GB laptop: put the Pi process, subagent runners, Git worktrees, and their state on remote compute. Use your laptop as a reconnectable client, not as the supervisor that must stay alive.

Checked September 25, 2026 · Prices, limits and credits change; verify before signup.

Fastest to try

Daytona

API-first sandboxes, web terminal, existing Pi integration, $200 initial compute credit. For your exact goal, run Pi inside a long-lived VM sandbox; the existing extension alone is insufficient.

Best recurring free compute

Oracle Cloud Always Free A1

Currently 2 ARM OCPUs + 12 GB RAM total and 200 GB storage; run one persistent host with all your worktrees. Harder signup and possible capacity/reclamation issues.

Simplest familiar UI

GitHub Codespaces

Browser access, GitHub login and monthly free quota. Excellent trial; idle shutdown and monthly hours make it unreliable as an unattended worker host.

The crucial distinction: A dropped SSH/browser connection does not have to kill agents if Pi and its child processes run remotely under a session manager such as tmux. But if the cloud machine itself stops, tmux stops too. A stopped Codespace or Daytona container will not continue a running task; a Daytona VM pause freezes progress until resumed. Pi's saved session preserves conversation history, not an in-flight process. Daytona lifecycle · Codespaces stop/start · Pi

What each option really buys you

1. Daytona — best first prototype Quickest automation

  • Provision VM sandboxes programmatically, run a browser terminal or reconnectable PTY, create multiple worktrees on one VM or one sandbox per job. Files persist; VM pause/resume can retain memory, but paused agents are not working. Disable auto-pause during active jobs and impose a max runtime / explicit cleanup. Persistence · PTY reconnect · Lifecycle caveats.
  • Important existing solution: @daytona/pi already offloads Pi's built-in file/shell tools, with session-to-sandbox reattachment. But the Pi agent, TUI and supervisor remain on your laptop; a separate subagent launcher and its local worktrees are not automatically moved. This does not solve your exact failure mode on its own. Extension README · Implementation.
  • Published rates: $0.0504/vCPU-hour + $0.0162/GiB RAM-hour, plus storage beyond the included allowance. Illustration: 6 × (1 vCPU, 2 GiB) ≈ $0.50/hour compute, so $200 buys ≈400 active fleet-hours, not 400 hours per agent. No promise those resources suffice for every workload. See pricing, billing / wallet expiry, pool limits.

2. Oracle Cloud Always Free A1 — best zero-recurring-cost target

  • As of this check, official docs for new Always Free tenancies say 2 OCPUs + 12 GB RAM total (older posts often say 4 / 24), plus 200 GB combined boot/block storage. One VM with a shared Git repository and six worktrees is a more direct match than six VMs. Always Free resources.
  • After one-time VM provision, Pi install, login/credentials, and tmux setup: normal SSH reconnects should not stop remote work. A browser terminal can be added later, but hosting and securing it is extra setup; SSH + tmux is the minimal reliable path. No provider can let you issue new commands from a disconnected laptop; the point is that work continues and control returns on reconnect.
  • Tradeoffs: ARM64 compatibility, payment-card/signup verification, possible “out of host capacity” in the fixed home region, and reclamation of low-utilization free instances after a 7-day evaluation. Do not rely on it as guaranteed production capacity; push branches / back up state. Capacity · Reclamation.

3. GitHub Codespaces — easiest evaluation, not an always-on worker

  • Open repo in browser, install Pi and tmux in the codespace, and keep worktrees there; gh codespace ssh is optional. The 120 core-hours/month on GitHub Free personal accounts amount to 60 wall-clock hours on a 2-core instance, or 30 on a 4-core instance. Included usage · CLI SSH.
  • Idle timeout defaults to 30 minutes (maximum configurable 4 hours); on stop, running agents die, though files survive. Terminal output may count as activity, but it is not a reliable guarantee for quiet jobs. Stopped codespaces can eventually be deleted. Good for short attended sessions, not overnight autonomous coding. Timeout · Retention.

4–6. Modal, E2B, Google Cloud — useful but not my first choice

  • Modal: recurring $30/month compute credit and detach/reattach by sandbox ID, but a sandbox has a maximum 24-hour lifetime; persistence after that needs snapshots/volumes and restart orchestration. Better for self-built short-job dispatch than a simple Pi host. Pricing · Sandbox lifetime.
  • E2B: $100 one-time credit and 20 simultaneous Hobby sandboxes, but Hobby runs are limited to an hour. Good disposable task workers, not your durable parent Pi session. Pricing.
  • Google Cloud: genuinely recurring free e2-micro VM but approximately 1 GB RAM and 0.25 sustained vCPU. Useful as a tiny controller or relay, not as compute for many coding agents. Free Tier · Machine specs.

The smallest architecture that actually meets the brief

laptop: terminal/browser client ── reconnectable connection ──► remote VM
                                                        tmux: Pi parent + supervisor
                                                        Pi child processes / async runs
                                                        repo + Git worktrees on remote disk
                                                        Git remote: durable commits/PRs
  1. One-time: choose Daytona VM for speed or Oracle A1 for recurring free RAM; install compatible Node, Pi, Git, tmux and your pi-subagents extension on the remote host. Authenticate Pi's model provider there; do not blindly copy your laptop's entire credentials directory.
  2. Each project: clone remotely once; have the remote Pi supervisor create remote Git worktrees and spawn remote child processes. This keeps RAM, process state, and file paths in one environment. Existing local worktrees do not magically appear there.
  3. Connection drops: reattach to the same tmux session (via SSH or provider web terminal). SSH is a transport, not the keeper of the process. If you need browser-only access on Oracle, that means an additional, properly authenticated web-terminal service.
  4. Guardrails: active Daytona VM must not auto-pause during a job; cap job duration and costs, persist run IDs / sandbox IDs, and push finished branches. On a failed VM, in-memory state is lost even if Git history remains. Confirm free-tier quotas before scaling.

For nicobailon/pi-subagents specifically: its documented Herdr saved-machine placement can run native Pi children remotely, but requires Herdr, per-machine credentials and repo preparation; managed worktrees are rejected for saved-machine placement. Running the whole supervisor and its worktrees on one remote machine is less moving machinery. Agent machine / worktree constraints.

If you turn this into a Pi extension

Build a thin launcher/reconnector, not another remote file-tool wrapper: /cloud start provisions or selects a VM, installs/bootstrap once, records the VM ID and repository, starts a named remote tmux/Pi session; /cloud attach reconnects; /cloud status shows state, quotas and cost; /cloud stop only stops when no jobs are active. Keep the mapping durable and treat a dropped connection as detach, never destroy. A local Pi extension cannot guarantee the local supervisor keeps running after the laptop sleeps. Start with one provider and one VM; add per-agent sandboxes only if isolation or CPU contention actually requires it. Pi extension lifecycle · Prior art: Daytona Pi extension.
